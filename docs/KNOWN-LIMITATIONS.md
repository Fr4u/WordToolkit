# Known limitations

WordToolkit deliberately avoids claiming complete Microsoft Word parity.

- The engine preserves unknown OPC parts, but it cannot semantically edit every ECMA-376/ISO 29500 extension. It now reads typed content-control properties, physical and built-in Custom XML stores, restricted binding targets and repeating-section topology, but it cannot update Custom XML values, refresh bound display content, execute general XPath, insert/delete repeating items or losslessly mutate SDT properties. Office 2013 rich-text binding content is identified, not decoded or rewritten. See `CONTENT-CONTROL-BINDING-GRAPH.md`.
- LaTeX and UnicodeMath parsers cover the documented structural subset, not every macro, package, spacing command or ambiguous linear syntax. OMML-to-LaTeX/UnicodeMath/MathML conversion is best-effort. Unsupported syntax fails instead of becoming an image.
- Equation numbering uses a `SEQ Equation` field and bookmark with a separate numbering paragraph. Complex journal-specific tab-stop/equation-table layouts need a template-specific extension.
- The saved-package engine now pairs bookmarks, parses nested complex/simple fields and projects Word bibliography source collections from Custom XML. Unique case-insensitive CITATION tags resolve to concrete source nodes; duplicate, missing or repeated singleton identity fields remain unresolved. Bibliography value fingerprints are process-scoped HMAC equality tokens, while stable `wbs_` selectors are not confidentiality boundaries. This layer does not evaluate or refresh fields, execute bibliography XSLT, render a formatted bibliography, validate source-type-specific required fields, update sources or rewrite references. Word/LibreOffice remains authoritative for TOC, PAGE, NUMPAGES, REF and bibliography field results; cached values may be stale before an office application refreshes them. TOC/TOF/TOT option semantics, captions, element hyperlinks and safe field-range edits are not complete. Word Live allowlisted fields are immediately updated, but pagination-dependent values can still change when layout, printers or later content changes.
- The unified saved-package dependency graph currently joins OPC relationships and reachability, projected semantic containment, styles, numbering, field/bookmark targets, bibliography collections/sources and resolved CITATION tags, section header/footer bindings, classic chart/series/axis/related-part dependencies, logical figures/representations/resources/caption associations, content controls, physical/built-in XML stores, binding targets, repeating-section items, nested tables and vertical-merge continuations. It does not yet type advanced DrawingML/VML layout, Office 2016 extended charts, SmartArt internals, full OLE, macros, signatures, encryption or co-authoring sessions. An absent edge in one of those domains is missing coverage, not proof that no dependency exists. The graph is read-only and does not itself repair, optimize or authorize a deletion.
- The saved-package Markup Compatibility graph is read-only. It evaluates the ECMA-376 Part 3 fifth-edition reference model only against explicitly supplied understood namespace URIs and application-defined extension expanded names; it does not guess an Office version profile. It inventories legacy `PreserveElements` and `PreserveAttributes` hints but does not execute them as current-edition rules. It does not yet emit a transformed MCE output document, serialize a branch edit, maintain compatibility declarations after namespace-changing mutations, or prove behavior against every Word build. A selected branch is semantic evidence for the supplied configuration, not proof that desktop Word will render the extension correctly.
- The native saved-package linter is an initial 18-rule layer, not Word's complete Accessibility Checker, security scanner or document-quality oracle. It covers bounded core/style/accessibility/security evidence and reports explicit unmodeled domains, but it does not yet understand full numbering sequence behavior, language, reading order, link quality, contrast, chart/SmartArt semantics, macros, signatures, encryption, co-authoring or every Word extension. It still materializes the typed graphs; its stricter 100,000-node/200,000-edge dependency ceilings reject oversized analyses but do not remove the underlying allocation debt. Linting itself is read-only. The only finding-bound executable repair is a reviewed replacement of exactly one existing, empty, lexically safe `dc:title`; missing/duplicate/mixed-markup title elements and every other finding fail closed. An unused-style finding names `delete_unused_style` but remains `implemented=false`; the separate semantic command re-proves deletion safety and is not authorized by the finding alone. Lint-repair apply blocks signed packages and new Open XML validation errors and only creates a new same-extension output file.
- Semantic indexing is currently a bounded single-process acceleration layer, not a durable search database. A handle covers one immutable package fingerprint, at most 100,000 nodes and one million property occurrences; the runtime keeps no more than four handles or 250,000 cached nodes, expires them within 30 minutes and loses them on restart. It indexes exact kind/part/property postings and can derive strict ancestor/descendant candidate sets with one tree propagation, but it has no full-text tokens, durable relationship postings, embeddings or multi-document ranking. Parent/child, sibling and arbitrary dependency-graph axes are not query predicates. Raw document text stays in process memory as part of the semantic projection and is never returned by index management, but it is not encrypted in memory. Callers should release handles as soon as repeated queries finish.
- Saved-package semantic style mutation can create a minimal inherited paragraph,
  character, table or numbering style, losslessly clone one existing definition,
  consolidate an explicitly selected custom, non-default source into an existing
  same-type target when their complete canonical definitions are identical after only
  identity and same-batch relation normalization. Consolidation updates recognized
  references in projected stories, revision snapshots, glossary metadata, `styles.xml`
  and `numbering.xml`, deletes the source definition and retains an exact inverse. The
  explicit `delete_unused_style` command can remove a custom, non-default definition, or
  a closed batch of mutually dependent definitions, only when no surviving modeled or
  unmodeled consumer refers to it. `rename_style` changes only the primary visible
  `w:name` of an explicitly selected custom, non-default style while preserving its
  stable internal `w:styleId`, aliases, formatting and ID-based references. It blocks
  ID/name/alias collisions, latent-style name consumers, name-addressed or ambiguous
  `STYLEREF` fields, macros, `altChunk`, linked-template updates, unmodeled field
  consumers and `stylesWithEffects`; it does not guess at field rewrites. These
  operations are deliberately not a
  fuzzy duplicate merger: existing style/numbering graph issues, non-equivalence,
  chained targets, `stylesWithEffects`, macros, `altChunk`, automatic linked-template
  updates, matching latent-style exceptions, dynamic/ambiguous/source-addressing
  `STYLEREF`, malformed unmodeled XML and explicit source references in unmodeled XML all
  block the plan. Linked paragraph and
  character styles require one explicit equivalent-pair batch.
  The same command family can
  assign a compatible inheritance-resolvable paragraph/character/table style to exact or
  selected semantic nodes in the same atomic transaction. `create_style` does not accept
  arbitrary formatting blocks; `clone_style` preserves source formatting and opaque
  extensions but deliberately strips default and linked-style identity. The engine does
  not change stable style IDs, delete referenced or built-in definitions, fuzzily repair, or align
  definitions to templates; infer domain labels such as APA/IEEE; model conditional table-style
  rendering; or enforce document protection/permission semantics. Definition edits fail
  closed when `stylesWithEffects.xml` exists because mirrored mutation is not implemented.
  Planning and apply are bounded to 200 resolved operations and block signatures and new
  SDK validation errors. Bulk selectors are limited to 16 commands and 200
  resolved nodes; they support one paragraph/run/table kind plus bounded text, exact
  properties, ancestry/descendancy, subtree and source-part predicates. They reject an
  empty result but cannot directly express property absence, sibling/adjacency, arbitrary
  dependency-graph reachability, linguistic document roles such as “theorem”, or an
  indexed multi-document query.
- Dependency-graph limits of one million nodes and two million edges remain absolute rejection counts, not ordinary operating targets. The graph keeps its deterministic 128 MiB `dependency_graph_accounted_v1` budget and 65,536-character key/metadata ceilings. `inspect_ooxml_dependencies` additionally creates one 640 MiB `word_operation_accounted_v1` lease before ZIP central-directory materialization and passes it through OPC retention/metadata, XML parsing, semantic and every typed projection plus the final graph. A public non-seekable Engine stream is copied through a delete-on-close temporary file capped at 576 MiB before the same preflight; it is not buffered without limit in memory. The calibrated 99,997-node point consumes 539,282,576 accounted bytes (80.4% of the ceiling). This is a cumulative conservative allocation proxy, not an exact CLR heap, simultaneous live-set or resident-memory cap; it intentionally charges repeated parsing and does not release earlier-stage charges. Shared immutable parsed-story storage, dense cross-domain calibration and independent hostile-corpus measurements remain missing. See `docs/benchmarks/2026-07-23-operation-resource-lease-windows-x64`, `docs/benchmarks/2026-07-23-windows-x64`, `docs/RESEARCH-DEPENDENCY-GRAPH-MEMORY-2026.md` and `docs/RESEARCH-OPERATION-RESOURCE-LEASE-2026.md`.
- General Word Live formula fields intentionally accept only bounded numeric expressions and deterministic allowlisted functions. Inputs use a period for decimals and a comma between function arguments; WordToolkit translates these to Word's active locale before insertion. Table-cell references remain rejected there. The dedicated table-formula tools generate positional or A1-style references from typed coordinates, but currently require a uniform rectangular table and support only `SUM`, `AVERAGE`, `COUNT`, `MAX`, `MIN` and `PRODUCT`. They do not accept arbitrary expressions, bookmarks, merged-grid addressing or raw switches. `update_live_word_table_fields` can refresh up to 5,000 existing fields in one selected table, but it intentionally updates the complete table `Fields` collection rather than accepting or rewriting field codes.
- Word Live can create bounded named bookmarks over newly inserted text and use them as `REF` targets. It does not yet rename, move or delete existing live bookmarks, and it rejects collisions instead of silently replacing an existing range.
- Adaptive structure learning discovers native enum values and property availability, reduces repeated failed probes and supports bounded semantic inspection of 23 native collections. It does not invent mutation support: comments, inline images, notes, headers and footers now have dedicated native editors, while a detected content control or unsupported drawing still requires an explicit editor, a verified member capability or the isolated workflow.
- The installed object-model catalog describes the public COM surface exposed by the local Word type library and derives one stable capability profile per member. It does not prove that every member is safe in every document state, read undocumented internal behavior or make WordToolkit equivalent to Word's entire user interface. Only policy-approved capability IDs are executable; unknown, external, global, lifecycle, event, restricted and sensitive effects remain blocked. The catalog is cached only for the MCP process lifetime, so a cold process pays the installed-type-library scan again.
- Structure item indexes and Range coordinates describe the connected live version; they are not durable identifiers after the user or another process edits Word. Re-inspect after a version or selection change.
- Word's Undo dropdown is an undocumented CommandBars surface. Guarded Undo fails closed when that history is unavailable, when the top entry is not labeled `WordToolkit:`, or when its token is stale. It deliberately cannot undo multiple entries in one request.
- `Comment.Done` and `Document.TrackRevisions` do not reliably participate in Word custom Undo. Their dedicated actions use verified assignment plus manual rollback on failure and do not promise a Ctrl+Z entry.
- `wordtoolkit.transform_ooxml_package/1.0` is deliberately narrow. Replacement scans only ordinary text in main-document paragraphs, replaces the first occurrence, excludes OfficeMath and refuses tracked-revision or MCE ambiguity; it is not a regex, whole-package search or semantic rewrite API. Accept/reject-all supports only the proven review-planner subset. Paragraph-mark merge requires an immediate following paragraph with no paragraph properties and no tracked revision content. Signed packages, same-path writes and existing outputs are blocked, and the operation does not remove or re-sign signatures on the caller's behalf.
- The saved-package review graph itself is read-only. A separate guarded review-decision planner/applicator can accept or reject its explicitly supported tracked-revision subset through source-linked byte-span mutations. It does not resolve/delete comments, add reactions, enforce permissions, model collaboration sessions or implement every revision family. Unsupported or ambiguous structures fail closed. Reaction payload semantics remain opaque inventory, and author/person matching cannot prove a live identity.
- The saved-package engine exposes a canonical source-linked OfficeMath read graph for all standard OMML object families, but it does not yet provide general cross-format LaTeX/UnicodeMath/MathML/OMML round trips, mathematical-equivalence proof, structural equation edits or repair. Separately, the native Word COM insertion path performs bounded immediate OMML readback for sensitive structures and checks canonical content, symbol counts, differential ancestry and style/control placement before committing. It preserves all four OfficeMath styles and fourteen representable MathML variants; the contextual Arabic `initial`, `tailed`, `looped` and `stretched` variants are rejected because the linear Word path cannot preserve them losslessly. That verifier is deliberately narrower than the saved-package graph and still cannot prove that two mathematically equivalent notations mean the same thing.
- The built-in comparison is paragraph/word oriented. It does not reproduce Microsoft Word's proprietary comparison behavior for moves, formatting-only changes, text boxes or every story.
- LibreOffice rendering can differ from Word in font substitution, pagination, line breaking, floating objects and Office Math. Automated visual checks are heuristic, not semantic vision review or pixel comparison.
- The current visual auditor detects blank pages and physical-edge clipping. It cannot reliably prove that a table split is aesthetically correct, a heading is contextually orphaned, or a glyph is merely ugly.
- Cross-platform CI cannot exercise the COM bridge. Normal CI runs the engine tests on Linux and both .NET suites plus the final plugin build on clean Windows. The licensed self-hosted Word gate is separate: tag pushes and manual runs execute the complete live-action acceptance, create an explicitly disposable document, close and reopen it, and clean its artifacts. Quitting is tested only when the gate owns an otherwise empty Word instance; it is skipped rather than destroying an existing user session.
- JSON-RPC messages are bounded to 8 MiB and active requests can be cancelled. Cancellation is cooperative. A queued COM operation can be skipped, but Windows COM provides no safe general-purpose way to abort a call already executing inside Word. WordToolkit refuses new live work while such a cancelled call remains active; if it never returns, the supervisor must restart only `wordtoolkit-native.exe`, never `WINWORD.EXE`, then reconnect and re-inspect state.
- Version-1 `.wtpatch` artifacts are ZIP containers holding deduplicated exact before/after payloads, not lightweight deltas. The codec currently materializes payloads as byte arrays. After measurement, defaults were reduced to 128 MiB total, 64 MiB per blob, a 4 MiB manifest and a 100:1 compression ratio; callers can explicitly configure higher ceilings. A 400 MiB-payload benchmark under the former ceiling peaked at 2,158.1 MiB of process memory. Every ceiling remains a rejection bound, not workload guidance. Raw patches verify hashes and canonical structure but are not encrypted or author-authenticated. An optional engine-level envelope supports AES-256-GCM and ECDSA-SHA256 with a bound signer key ID; it requires caller-managed 32-byte encryption keys and trusted ECDSA public keys and is not yet exposed as an MCP key-management workflow.
- The optional Microsoft Open XML SDK validator is built in Docker. Local Python-only environments report it unavailable and rely on WordToolkit's structural validator.
- OAuth tokens are verified against an external standards-compliant identity provider; WordToolkit is a resource server and does not implement user login or dynamic client registration itself.
- Session metadata and locks are in process memory. Production is limited to one application replica until a shared backend is implemented.
- The remote service's 33 ordinary draft mutators are now isolated copy-on-write
  transactions: partial operation and candidate-validation failures leave the active
  engine and version unchanged. `apply_document_operations` can compose 1-16 of them as
  one ordered process-local transaction with a 1 MiB aggregate JSON-argument ceiling,
  one final validation and one version advance. It has no best-effort mode, arbitrary
  method dispatch or references to IDs created by earlier operations. This is
  process-local isolation, not crash-durable
  persistence. Each edit currently serializes the full active package twice, opens a
  clone and validates the candidate because immutable shared parsed-part storage does not
  exist. A 15-sample local one-paragraph benchmark measured 56.319 ms candidate-
  preparation median versus 0.160 ms for the old unsafe direct mutation (+56.159 ms,
  351.99x). It excludes engine creation, commit swap, replaced-workspace cleanup and MCP
  dispatch; the optional Microsoft SDK validator was unavailable. Package size and SDK
  validation can increase the whole-request cost. The active clone deliberately retains
  its checkpoint, candidate package and extracted work directory until the next swap or
  close, so large drafts also carry a sustained per-open-document disk cost. No dedicated
  workspace quota or disk-pressure metric exists yet. Batch image inputs use a top-level
  `files` array and `file_index`, then are staged and decoded before the document lock.
  Partial downloads are removed on failure/cancellation, but a complete staged upload
  can remain against session quota after a later operation fails even though the
  document itself is rolled back.
- The current local Codex plugin is a self-contained Windows x64 .NET runtime and does not need `uv`, Python or a virtual environment. It still cannot run in ChatGPT web or on a phone because those surfaces cannot automate the user's desktop Word process.
- No public deployment is included in source-control credentials. Remote use
  still requires an operator-owned HTTPS domain and identity provider.
